# WFI Full-Pipeline Refactor Plan

**Branch:** `refactor/full-pipeline`
**Plan recorded:** 2026-11-13, before pipeline implementation
**Run gate:** the 20261113 relative-response fit is complete for WFI01–WFI18
(256/256 tile archives and rate tables per detector); no WFI fit process remains
active.

## Decisions from the user

- The calibrated-data reduction runs only on Nexus. Do not refactor its runtime
  code here; document the Nexus procedure and its output/handoff.
- The local model pipeline starts from the corrected-statistics directory
  transferred from Nexus.
- Relative-response is the regular/default route. Full TMM is the occasional,
  more expensive alternative. A run selects exactly one route.
- Both routes should produce the model bundle, joint-modulated fit, modulated
  bundle, final Eric-reader H5, and diagnostics.
- Production TMM and joint-fit plots are generated by default.
- Group outputs for each run under one output root inside the data folder, with a
  central `logs/` directory.
- Archive standalone scripts used only for experiments or bespoke analysis. If
  a script contains functionality required by production, extract that
  functionality into the active pipeline first.

## Current findings

- `README.md` describes a Nexus entrypoint named `run_wfi_reduction_pipeline.py`,
  but that file is absent from the current local tree. Its historical 6,819-line
  implementation was removed in commit `7cd19ca`. This refactor will document
  the Nexus command and artifacts, not recreate or change the reducer.
- `wfi_pipeline/run_wfi_production.py` contains the full-TMM production defaults and dispatches
  cached relative-response fits when `--response-cache-root` is supplied. The
  relative runner is currently invoked per detector. The refactored frontends
  must preserve the production defaults while selecting detectors explicitly
  and running them sequentially.
- The regular relative-response path consumes the pinned 20261109 six-LED cache;
  it must not build a replacement cache. It still emits a full-wavelength bundle
  by evaluating the pinned source TMM optical state over the bundle wavelength
  grid.
- The full-TMM path must run the full model and derive the response artifacts
  required by the same bundle/joint-modulation/H5 stages from that run's fit
  outputs. It must not mix full-TMM and relative-response outputs within a run.
- The current H5 chain is manual and spans fit, base/modulated bundle, global
  reflectance modes, history reference, prototype assembly, and unchanged-reader
  packaging. The final H5 must retain Eric's original dataset inventory and
  continue to load through the unchanged reader.
- The current joint fit retains full independent tile histories. Eric's current
  v3 deposition group can express only the exported rank-one approximation; the
  approximation metrics and CAR190 baseline-aligned comparison must remain
  visible in the output manifest/reports.
- Existing in-progress documentation edits in `README.md` and the WFI production
  docs are user work and must be preserved.

## Target command interface

Use two clearly named top-level commands so choosing a fit route does not expose
model-tuning knobs:

```bash
python run_wfi_relative_response_pipeline.py \
  --input-path <Nexus-corrected-statistics-directory> \
  --output-path <data-folder>/production/pipeline_runs/<run-name>

python run_wfi_full_tmm_pipeline.py \
  --input-path <Nexus-corrected-statistics-directory> \
  --output-path <data-folder>/production/pipeline_runs/<run-name>
```

The relative-response command is the normal route; it uses the pinned cache and
does not rebuild it. The full-TMM command runs the expensive fit. The command
name selects exactly one route; no detector selection, priors, optimizer
tolerances, grid values, cache switches, or wavelength settings are required
from the operator. Defaults are centralized, versioned, and recorded in the run
manifest. Optional explicit detector selection may be retained only as a
development/test facility, not as a production default.

## Output layout

Each invocation owns one output root inside its data folder:

```text
<output-path>/
  pipeline_manifest.json
  logs/<stage>/<detector-or-all>.log
  corrected_statistics_4h_thinned/       # created only for unthinned input
  production/
    <detector>/<selected-model-route>/
      fits/tile_000/...
      experiments/<joint-fit-name>/...
    caches/six_led/<route>/<detector>/...
    caches/spectral_response/<route>/<detector>/...
    wavelength_response_bundle/
      wfi_all_2nm_rank16.npz
      wfi_all_2nm_rank16_modulated.npz
      intermediates/h5/                  # build-stage products, not releases
        tmm_joint_modulated_reflectance_modes.h5
        joint_ice_history_reference.h5
        ice_response_model_prototype.h5
      final/
        joint_modulated_v2.h5
        joint_modulated_v2.validation.json
    plots/<route>/car201/...
```

Per-detector TMM plots live beside that route's fit archives. The local
relative-response run uses the pinned six-LED cache outside its output tree;
the full-TMM run stores its newly derived six-LED cache under its run root. The
two portable NPZ filenames remain the exact stable upload keys; route identity
is recorded in the manifest and bundle metadata instead of suffixing filenames.

The manifest records the selected route, input fingerprints, resolved defaults,
source cache provenance, per-detector completion, product paths, and output
hashes. Re-running into an existing output root must either resume compatible
checkpoints or fail clearly rather than mix model routes. The production
orchestrator runs WFI01–WFI18 sequentially with explicit detector selections.

## Implementation sequence

1. **Centralize production profiles.** Add one defaults/config module for the
   validated full-TMM and relative-response profiles. Keep the numerical model
   implementations in shared modules; the new named scripts are small,
   path-only orchestrators.
2. **Document the Nexus boundary.** Document the existing Nexus-only reducer's
   invocation, inputs, corrections, output directory structure, and corrected
   statistics handoff. Do not copy or alter its runtime code locally.
3. **Add the relative-response frontend.** Consume the supplied corrected
   statistics path and pinned 20261109 cache path from the production profile;
   do not invoke any six-LED cache builder. Run the independent per-detector fit,
   produce TMM-evaluated full-wavelength base bundle, and run fit plots.
4. **Add the full-TMM frontend.** Run the full TMM fit using its production
   defaults, build the full-wavelength bundle from that fit, then derive the
   six-LED/relative-history inputs required by the common joint-modulation stage
   from the same full-TMM optical state. Keep every artifact under this run's
   output root.
5. **Automate the common joint/export stages.** Run the reader-compatible
   CAR190 + Amber fits sequentially for all 18 detectors; retain full histories
   in those fits; build the modulated full-wavelength `.npz`; construct the
   reflectance/history intermediates; package the final H5; run unchanged-reader
   validation and generate the joint diagnostic plots automatically.
6. **Archive exploratory scripts.** Use import and test dependency scans before
   moving standalone one-off experiments and bespoke analyses into
   `archive/exploratory/<topic>/`. Keep active production modules, production
   plotting entrypoints, and regression tests out of the archive. Preserve
   original paths/purpose in an archive index; do not move data products.
7. **Validate and migrate.** Preserve 20261111/20261113 outputs as the golden
   reference. Run fast fixture tests on every change, then a full relative-path
   validation and a less frequent full-TMM validation. Check the output
   manifest, logs, and generated plots before declaring a run complete.

## Regression test plan

- **Nexus handoff:** locally validate a small fixture with the expected corrected
  sufficient-statistic fields, 1039/1063 coverage, and thinning manifest. Mock
  network/telemetry providers; never require Nexus or MAST in unit tests.
- **Default/config tests:** assert each named frontend resolves the fixed current
  defaults, records them in the manifest, selects exactly one route, and blocks
  a mismatched cache or stale output root.
- **Fit branch tests:** small fixture runs for full-TMM and cached relative
  response, checking tile coverage, positive/nondecreasing histories, cache
  provenance, reset/gray metadata, and expected files.
- **Bundle tests:** verify `.npz` schemas, detector/tile completeness, stable
  wavelength/thickness/time grids, zero-thickness unity, direct-TMM samples,
  and modulation reconstruction.
- **Joint-fit tests:** verify 18 converged summaries, source/SED sample identity,
  full per-tile histories, CAR190/Amber objective summaries, and roll/gray
  handling.
- **H5 tests:** exact original dataset path/rank/dtype-kind inventory, all-18
  unchanged-reader responses finite, fitted gray factors/reset epochs, no extra
  groups or AR parameters, and explicit rank-one history-error tolerances.
- **Correction regression:** CAR190 comparisons must apply the saved per-tile/LED
  baseline and gray terms; raw public-reader log changes alone are not the joint
  fit's CAR190 objective. CAR201 comparisons use the same cohort, roll offsets,
  effective-area support, and epoch/filter aggregation for both models.
- **End-to-end smoke:** run the refactored relative path on a tiny offline fixture
  through the final H5, confirm restart behavior and the complete manifest/log
  tree. Full 20261111 byte hashes are for immutable inputs; generated `.npz`/H5
  files are compared semantically with tolerances because they include volatile
  timestamps/paths and may vary slightly by numerical library version.

## Refactor guardrails

- Preserve the validated model defaults and the full-TMM/relative-response
  distinction; do not create a blended model route.
- Keep the relative-response cache as an input artifact for the regular route,
  not a build step.
- Do not change Eric's reader or H5 schema; no AR parameters or custom
  photometry-weighting groups are exported.
- Keep S3 publication separate and explicit; a local pipeline run does not
  upload or delete remote objects.
- Keep logs, manifests, and model products under the user-provided output path,
  inside the data folder.
